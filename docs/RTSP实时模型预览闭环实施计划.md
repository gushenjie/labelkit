## 1. 实施目的

本计划用于指导 LabelKit 实现训练模型的单路 RTSP 实时预览能力。用户在模型中心选择一个已经训练完成的目标检测模型，输入可访问的 RTSP 地址后，由 LabelKit Python 后端作为 RTSP 客户端拉取摄像头视频、执行模型推理并绘制检测框；浏览器只显示后端输出的带框画面、类别、置信度和实时状态，不直接连接 RTSP。

本计划是当前优先实施基线。原“模型一键部署业务平台”方案转为第二阶段规划，在本闭环完成真实摄像头验收前不进入实施。

## 2. 产品闭环与成功标准

本次实施解决的核心问题是验证训练结果是否能够直接作用于真实视频，而不是建设完整的视频监控业务平台。完整闭环如下：

```text
数据标注
   ↓
模型训练
   ↓
模型中心选择训练模型
   ↓
输入 RTSP 地址并启动预览
   ↓
后端持续拉流和模型推理
   ↓
浏览器实时显示视频、目标框、类别和置信度
   ↓
用户停止预览，后端释放摄像头与推理资源
```

实现完成后，应能通过一个真实训练模型和一条真实 RTSP 视频流证明以下结果：

1. 模型只在预览会话启动时加载，不在每一帧重复加载。
2. RTSP 视频可以持续读取，画面不会因推理速度低于摄像头帧率而无限积压。
3. 模型返回检测结果后，画面能够显示与当前帧对应的检测框；第一阶段不评价模型输出是否准确。
4. 页面能够展示连接、推理、重连、失败和停止状态。
5. 用户停止预览、关闭页面或会话超时后，摄像头连接、后台线程和模型引用能够释放。
6. RTSP 凭据不进入数据库、浏览器地址栏、业务日志或错误堆栈。

## 3. 实施范围

### 3.1 本次实现内容

系统应支持：

- LabelKit 训练产生的 Ultralytics YOLO `detect` 模型。
- 模型中心进入“实时预览”。
- 输入一条 `rtsp://` 或 `rtsps://` 地址。
- 配置置信度阈值和目标推理帧率。
- 后端使用 OpenCV/FFmpeg 拉取 RTSP 视频。
- 后端持续执行 YOLO 推理并生成带检测框的视频帧。
- 通过 MJPEG 将最新检测画面输出到浏览器。
- 页面展示模型、连接状态、推理耗时、推理帧率和当前目标数量。
- 手动停止、断流重连、空闲超时和异常资源释放。
- 每个登录用户最多一个活动预览会话，并限制服务端全局会话数。

### 3.2 明确不实现的内容

本次不建设以下能力：

- 摄像头资产库和摄像头持久化管理。
- 多摄像头宫格和轮巡。
- 告警规则、告警通知和告警记录。
- 录像、回放、截图归档和证据留存。
- 策略管理、设备管理和客户端下发。
- 跨项目共享预览会话。
- 模型一键部署至外部业务平台。
- WebRTC、HLS 或流媒体服务器集群。
- 人数统计、姿态、多模型关联、OCR 等算法专属后处理。
- 模型准确率、误报漏报、数据集修正、阈值调优和重新训练。

如上述能力在实现过程中被提出，应另行评估，不得直接并入本计划造成范围扩张。

## 4. 现有能力与改造依据

LabelKit 当前已经具备模型版本、模型中心、单张图片在线测试、目标框 Canvas 绘制、OpenCV 和 Ultralytics 推理能力。本次应复用这些能力，不重建模型目录或训练产物体系。

现有 `server/api/models.py` 中的图片推理接口会调用 `server/core/labeling.py` 的 `propose_yolo()`。该函数每次调用都会重新执行 `YOLO(model_path)`，适合单图片测试，但不能直接循环用于实时视频，否则会反复加载模型并造成不可接受的延迟和资源开销。

现有 `web/src/app/models/trial/page.tsx` 已经提供模型上下文、结果布局和图片测试交互，`web/src/components/ModelTrialPreview.tsx` 已经实现目标框与类别绘制。本次前端应延续现有在线测试视觉体系，增加“图片测试 / 实时预览”模式切换，不新建一套风格不一致的页面。

## 5. 技术方案

### 5.1 总体链路

普通浏览器不能直接播放 RTSP，因此 RTSP 连接和推理必须在 LabelKit Python 后端完成。

```text
RTSP 摄像头
    │
    ▼
OpenCV/FFmpeg 拉流线程
    │ 只保留最新帧
    ▼
YOLO 推理线程
    │ 目标框、类别、置信度
    ▼
Ultralytics 结果绘制 + JPEG 编码
    │
    ▼
FastAPI StreamingResponse（MJPEG）
    │
    ▼
浏览器实时预览区
```

### 5.2 传输方案选择

本次采用 MJPEG，不采用 WebRTC、HLS 或基于 WebSocket 的自定义视频协议。

选择 MJPEG 的原因如下：

- FastAPI 可以通过 `StreamingResponse` 直接输出。
- 浏览器使用 `<img>` 即可显示，不需要额外播放器。
- 检测结果可以直接绘制到服务端输出帧，避免视频帧与 JSON 检测框同步问题。
- 现有前端已经支持为图片资源 URL 附加认证信息，接入方式明确。
- 当前目标是单路模型验证，带宽和大规模并发不是主要约束。

MJPEG 不是长期多摄像头监控的最终传输方案。如果后续出现音频、亚秒级低延迟、大规模并发或浏览器端交互叠加需求，再单独评估 WebRTC。

### 5.3 视频帧处理原则

摄像头帧率通常高于模型推理帧率。系统不得将每一帧放入无限队列，而应采用“最新帧覆盖”模式：

1. 拉流线程持续读取 RTSP，只在内存中保存最新一帧。
2. 新帧到达时覆盖尚未处理的旧帧。
3. 推理线程按目标推理帧率读取当时最新帧。
4. 推理完成后保存最新 JPEG 和本次检测统计。
5. MJPEG 输出生成器只发送最新已完成帧，不补发历史积压帧。

此方案以实时性优先，不保证逐帧处理。页面显示帧率可以与推理帧率一致，本次不额外增加无检测结果的高帧率视频通道。

### 5.4 模型生命周期

每个预览会话应独占一个模型运行实例。工作线程启动后加载一次模型，会话停止后释放引用。本次不提前实现跨会话全局模型缓存，原因是全局缓存会引入显存淘汰、并发锁和引用计数等额外复杂度。

应通过全局预览会话上限控制显存和内存占用。默认全局最大会话数为 2，低显存环境可以配置为 1。后续只有在真实使用证明模型重复加载成为主要瓶颈后，才增加带引用计数和推理锁的模型缓存。

### 5.5 检测框绘制

后端应使用 Ultralytics 推理结果的绘制能力生成带框画面，保证目标框坐标与输出 JPEG 使用同一图像尺寸。输出内容至少包括：

- 目标框。
- 模型类别名称或类别索引。
- 置信度。

如果模型中文类别在当前绘制环境中无法正常显示，应优先保证目标框和置信度可见，并在页面右侧使用浏览器字体展示中文类别统计；不得为了中文字体绘制引入与本次闭环无关的复杂渲染系统。

## 6. 预览会话设计

### 6.1 会话状态

```text
STARTING
   ├── 模型加载
   └── RTSP 连接
          ↓
STREAMING
    ↓ 断流
RECONNECTING
    ├── 恢复成功 → STREAMING
    └── 超过重试上限 → FAILED

任意活动状态收到停止请求 → STOPPING → STOPPED
不可恢复异常 → FAILED
```

| 状态 | 含义 |
|---|---|
| `STARTING` | 会话已创建，正在加载模型和连接视频流 |
| `STREAMING` | 已持续产生推理后的 JPEG 帧 |
| `RECONNECTING` | 视频流中断，正在有限重连 |
| `STOPPING` | 已收到停止请求，正在释放资源 |
| `STOPPED` | 摄像头、线程和模型引用已释放 |
| `FAILED` | 模型、网络、认证、编码或推理发生不可恢复错误 |

### 6.2 会话内存结构

预览会话至少应保存：

- `session_id`
- `user_id`
- `project_id`
- `model_id`
- RTSP 地址，仅驻留内存
- 置信度阈值
- 目标推理帧率
- 当前状态和错误码
- 启动时间、最后访问时间和最后成功帧时间
- 最新原始帧及其锁
- 最新 JPEG 及其锁
- 最新检测数量、类别统计、推理耗时和实际推理帧率
- 停止事件
- 拉流线程和推理线程引用

会话对外序列化时不得返回 RTSP 密码。展示地址时只能使用脱敏结果。

### 6.3 线程职责

每个会话使用两个后台线程：

1. 拉流线程只负责打开 `cv2.VideoCapture`、持续读取帧、覆盖最新帧和处理断流重连。
2. 推理线程只负责加载模型、读取最新帧、执行推理、绘制结果、JPEG 编码和更新统计。

推理不得直接运行在 FastAPI 请求事件循环中。两个线程之间通过锁保护的单帧槽位交换数据，不使用无界队列。

### 6.4 会话限制与回收

- 每个登录用户最多一个活动会话。
- 默认全局最多两个活动会话，超过限制返回 HTTP 429。
- 相同用户创建新会话时，应先显式停止旧会话；不得静默抢占。
- 页面成功连接 MJPEG 时更新最后访问时间。
- 浏览器断开后允许短暂重连；连续 60 秒没有流消费者时自动停止。
- 连续读取失败时进入 `RECONNECTING`，使用有限退避重试。
- 服务端关闭时应停止全部会话，并等待线程在限定时间内退出。
- 停止接口应幂等，多次调用均返回最终状态。

## 7. 后端接口规格

### 7.1 创建预览会话

```http
POST /api/projects/{projectId}/models/{modelId}/preview-sessions
Content-Type: application/json
Authorization: Bearer {token}
```

请求示例：

```json
{
  "rtspUrl": "rtsp://camera-host/stream-path",
  "confidenceThreshold": 0.25,
  "inferenceFps": 5
}
```

校验要求：

- 项目和模型必须存在且模型属于该项目。
- 模型文件必须存在并可读取。
- 模型任务必须为目标检测。
- RTSP 协议只允许 `rtsp` 或 `rtsps`。
- RTSP 地址必须包含主机，不得接受空地址。
- 置信度范围为 0.01～1.00。
- 推理帧率范围为 1～10 FPS。
- 不得将 RTSP 地址拼接为 Shell 命令。
- 当前用户和全局会话数不得超过限制。

响应示例：

```json
{
  "sessionId": "uuid",
  "status": "STARTING",
  "streamPath": "/api/projects/project-id/models/model-id/preview-sessions/session-id/stream",
  "createdAt": "2026-09-09T10:00:00+08:00"
}
```

接口应快速返回，由后台线程完成模型加载和 RTSP 连接，避免模型冷启动占用请求超时时间。

### 7.2 获取会话状态

```http
GET /api/projects/{projectId}/models/{modelId}/preview-sessions/{sessionId}
```

响应应包含：

```json
{
  "sessionId": "uuid",
  "status": "STREAMING",
  "modelName": "v1",
  "frameWidth": 1920,
  "frameHeight": 1080,
  "inferenceFps": 4.8,
  "lastInferenceMs": 42,
  "detectionCount": 2,
  "classCounts": {
    "灭火器": 2
  },
  "lastFrameAt": "2026-09-09T10:00:08+08:00",
  "errorCode": null,
  "errorMessage": null
}
```

接口应验证会话归属，其他用户不得查询该会话。响应不得包含原始 RTSP 地址和密码。

### 7.3 输出 MJPEG

```http
GET /api/projects/{projectId}/models/{modelId}/preview-sessions/{sessionId}/stream?token={token}
```

响应类型：

```text
multipart/x-mixed-replace; boundary=frame
```

输出生成器应：

- 只返回当前会话的最新 JPEG。
- 没有首帧时等待短时间，不进行忙循环。
- 客户端断开时结束生成器并更新消费者状态。
- 会话进入 `FAILED` 或 `STOPPED` 后结束输出。
- 验证登录身份和会话归属。

鉴于 `<img>` 无法附加 `Authorization` Header，本接口可复用项目现有的查询参数 token 认证方式。RTSP 地址和摄像头凭据不得出现在 MJPEG URL 中。

### 7.4 停止预览会话

```http
DELETE /api/projects/{projectId}/models/{modelId}/preview-sessions/{sessionId}
```

停止接口应设置停止事件，关闭 `VideoCapture`，等待拉流和推理线程退出，并将状态更新为 `STOPPED`。接口应幂等，并验证会话归属。

### 7.5 错误码

| 错误码 | 场景 |
|---|---|
| `MODEL_NOT_FOUND` | 模型不存在或不属于项目 |
| `MODEL_FILE_MISSING` | 模型文件不存在 |
| `MODEL_LOAD_FAILED` | Ultralytics 无法加载模型 |
| `UNSUPPORTED_MODEL_TASK` | 模型不是 `detect` 任务 |
| `INVALID_RTSP_URL` | 地址为空、协议错误或缺少主机 |
| `RTSP_CONNECT_TIMEOUT` | 在规定时间内无法获得视频帧 |
| `RTSP_AUTH_FAILED` | 摄像头认证失败；无法精确识别时可归入连接失败 |
| `RTSP_STREAM_LOST` | 已连接视频流持续读取失败 |
| `UNSUPPORTED_CODEC` | 当前 OpenCV/FFmpeg 无法解码视频 |
| `PREVIEW_CAPACITY_EXCEEDED` | 用户或全局会话数超过限制 |
| `INFERENCE_FAILED` | 模型推理或结果绘制失败 |

无法从 OpenCV 错误信息可靠区分认证、网络和编码错误时，页面应显示连接失败及排查建议，不得伪造精确原因。

### 8.3 建议配置

```text
preview_max_sessions = 2
preview_connect_timeout_seconds = 10
preview_idle_timeout_seconds = 60
preview_default_inference_fps = 5
preview_max_inference_fps = 10
preview_jpeg_quality = 82
preview_max_frame_width = 1280

```

帧宽超过上限时，应等比例缩放后再推理和输出，控制显存、推理耗时和 MJPEG 带宽。实际默认值应在真实模型和摄像头基线测试后确认。

## 9. 前端页面设计

### 9.1 页面入口

模型中心的训练模型卡片应保留现有“在线测试”入口。进入后在同一页面提供：

- 图片测试。
- 实时预览。

默认保持图片测试，避免改变现有用户路径。用户选择实时预览后再显示 RTSP 配置，不在模型卡片直接暴露敏感输入。

### 9.2 实时预览布局

页面主体延续现有在线测试的左侧画面、右侧结果布局：

- 左侧显示实时视频、空状态、连接中状态、重连状态和错误状态。
- 右侧显示当前模型、模型版本、摄像头状态、画面分辨率、实际推理 FPS、最近推理耗时、目标总数和类别统计。
- 顶部提供 RTSP 地址、置信度、推理帧率、开始和停止操作。
- RTSP 输入应使用敏感信息友好的展示方式。启动成功后只显示脱敏地址，不回显密码。

### 9.3 前端状态管理

前端应维护：

- 当前模式：图片或实时。
- RTSP 输入和检测参数。
- 创建会话加载状态。
- `sessionId`。
- 后端会话状态。
- MJPEG 流地址。
- 状态轮询定时器。
- 页面卸载时的停止请求。

状态查询建议每秒执行一次；页面处于 `STOPPED` 或 `FAILED` 后停止轮询。重复点击开始时应禁用按钮，防止创建并发会话。

## 10. 安全与隐私要求

RTSP 地址常包含用户名、密码和内网地址，本次实现必须遵守以下要求：

1. RTSP 地址只通过创建会话的 HTTPS POST Body 发送。
2. RTSP 地址不得作为查询参数、页面路由参数或本地存储内容。
3. 后端只在会话内存中保存地址，会话结束后释放，不写数据库。
4. 日志只能记录会话 ID、项目 ID、模型 ID、脱敏主机和错误码。
5. 日志、异常和 API 响应不得返回用户名、密码或完整 RTSP 地址。
6. 地址只允许 `rtsp` 和 `rtsps` 协议，不得支持任意 URL 协议。
7. 不得使用字符串拼接 Shell 命令启动 FFmpeg，避免命令注入。
8. 接口必须要求用户登录，并验证模型和会话归属。
9. 全局会话限制和空闲回收必须生效，防止通过大量会话耗尽 GPU、内存和线程。
10. 如系统未来开放给低信任租户，应增加可访问网段白名单和更细粒度权限；本次不得宣称已经解决全部服务器端网络请求伪造风险。

## 11. 故障处理要求

### 11.1 首次连接失败

连接在超时时间内没有获得有效帧时，会话应进入 `FAILED`。页面应提示用户检查：

- RTSP 地址和路径。
- 摄像头账号密码。
- LabelKit 后端到摄像头的网络连通性。
- 摄像头是否允许并发连接。
- OpenCV/FFmpeg 是否支持当前编码。

### 11.2 运行中断流

已经进入 `STREAMING` 后连续读取失败，应进入 `RECONNECTING`。重连采用有限退避，不得高速死循环。达到重试上限后进入 `FAILED` 并释放资源。

### 11.3 模型加载或推理失败

模型加载失败时不得继续打开长期 RTSP 会话。推理连续失败超过限制时应停止会话，并记录不包含敏感输入的错误摘要。单帧偶发失败可以丢弃该帧，但必须计数并避免无限吞掉异常。

### 11.4 浏览器断开

MJPEG 消费者断开后，不立即停止会话，为页面刷新保留短暂恢复窗口。超过空闲时间仍无消费者时自动停止。页面主动点击停止时不等待空闲超时。

## 12. 性能与资源基线

本次不以摄像头原始帧率作为推理帧率目标。产品目标是检测结果具有实时感并且延迟不持续累积。

初始验收基线如下：

| 指标 | 初始要求 |
|---|---|
| RTSP 首帧时间 | 在批准的真实环境中不超过 15 秒 |
| 目标推理帧率 | 默认 5 FPS，可配置 1～10 FPS |
| 最低可接受实际推理帧率 | 真实验收模型上不低于 3 FPS |
| 端到端画面延迟 | P95 不超过 2 秒，且运行过程中不持续增长 |
| 连续运行 | 单会话连续 30 分钟无崩溃、无明显内存持续增长 |
| 停止释放 | 用户停止后 5 秒内进入 `STOPPED`，摄像头连接和线程退出 |
| 会话容量 | 默认最多 2 个，根据显存基线可降为 1 |

若真实模型无法达到最低推理帧率，应先降低输入分辨率或推理帧率。仍无法通过时，应明确展示硬件性能不足，不得通过缓存旧帧伪造流畅效果。

## 13. 测试计划

### 13.1 后端单元测试

- RTSP URL 协议、主机、阈值和帧率校验。
- 模型不存在、模型不属于项目、模型文件缺失。
- 每用户单会话和全局容量限制。
- 会话状态合法转换。
- 拉流线程只保留最新帧，不形成无界队列。
- 模型每个会话只加载一次。
- 停止接口幂等。
- 浏览器断开后的空闲超时回收。
- 敏感 URL 脱敏和错误响应不泄露密码。
- 服务关闭时所有活动会话释放。

OpenCV、YOLO 和时间相关行为应通过可替换依赖或 Mock 测试，避免单元测试依赖真实摄像头和 GPU。

### 13.2 后端接口测试

- 创建会话返回 200/201 和有效 `sessionId`。
- 未登录访问返回 401。
- 访问他人会话返回 404 或 403，项目内口径应统一。
- 超过容量返回 429 和明确错误码。
- 状态接口返回脱敏、稳定的数据结构。
- MJPEG 接口返回正确 `Content-Type` 和帧边界。
- 删除会话后再次查询得到明确停止状态或统一的不存在语义。

### 13.3 前端测试

- 图片测试默认保持可用。
- 切换实时预览后显示 RTSP 配置。
- 创建过程中按钮禁用，防止重复提交。
- 会话成功后显示 MJPEG 和实时指标。
- 连接失败、模型失败、重连和容量不足均有明确页面状态。
- 点击停止后画面和轮询结束。
- 离开页面触发停止请求。
- RTSP 密码不写入 URL、LocalStorage 或错误提示。

### 13.4 真实环境验收

应使用至少一个 LabelKit 真实训练模型和一条真实 RTSP 摄像头流完成平台链路验收。必须确认模型输出的检测框能够随当前视频帧持续更新，但第一阶段不以特定模型的识别准确率、误报率或漏报率作为平台交付门禁。

需要执行：

1. 正常连接并持续预览 30 分钟。
2. 确认模型返回的检测框、类别和数量随当前帧同步更新。
3. 修改置信度阈值，确认请求参数生效；不评价某个模型的业务准确率。
4. 主动断开摄像头网络，确认重连和失败状态。
5. 使用错误密码，确认错误中不泄露凭据。
6. 关闭浏览器页面，确认会话在规定时间内回收。
7. 重复启动和停止，确认线程数、内存和显存不持续增长。
8. 使用错误或不兼容模型，确认会话失败且服务整体保持可用。

- 页面准确展示运行、重连、失败和停止状态。
- 用户停止、页面关闭超时和服务关闭均能释放资源。
- RTSP 凭据没有写入持久化存储、URL 或日志。
- 单元测试、接口测试、前端测试和现有图片测试回归通过。
- 真实环境单路连续运行与异常场景验收通过。

第一阶段交付结论只覆盖平台执行与展示能力，不代表所选模型已经达到业务准确率要求。模型误报、漏报和泛化能力应作为独立训练验收处理，不反向扩大本计划为模型优化项目。

达到上述标准后，再根据实际用户需求决定是否启动第二阶段的跨平台一键部署，不提前为未验证的扩展增加架构复杂度。
