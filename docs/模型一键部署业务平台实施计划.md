## 1. 文档目的

本文档规定 LabelKit 训练平台与 AI Box 业务平台之间的模型部署衔接方案。目标是在 LabelKit 模型中心完成训练后，由用户发起一次部署操作，系统自动将模型文件和模型元数据交付至业务平台，创建或复用算法、模型、模型版本、默认策略和策略规则，并允许用户继续在业务平台为摄像头绑定该策略。

本文档同时明确动态算法的能力边界、跨系统接口、部署状态、失败恢复、客户端生效确认、安全约束、实施顺序和验收要求，作为三个项目后续开发、联调和验收的共同基线。

## 2. 建设目标与范围

### 2.1 建设目标

系统应实现以下端到端闭环：

1. LabelKit 训练成功后应形成可部署的模型版本，保留模型文件、训练来源、类别信息、指标和数据集版本等追溯信息。
2. 用户应能在 LabelKit 模型中心发起一次部署操作，不需要手工下载模型、复制文件或在业务平台重复录入算法和模型信息。
3. 业务后台应统一负责模型文件入库、业务资源创建、版本发布、幂等控制、失败恢复和回滚，不允许 LabelKit 直接写业务数据库。
4. 同一个 LabelKit 项目应稳定映射到同一个业务算法、模型和默认策略；重新训练并部署时只新增模型版本和对应规则，不重复创建算法。
5. 模型部署不应自动绑定摄像头。用户应在业务平台确认算法和策略后，自主选择需要绑定的摄像头。
6. 客户端应在不中断旧模型推理的前提下下载、校验、加载并切换新模型，并向业务后台报告实际生效结果。
7. 完成一次客户端基础能力升级后，后续新增通用单模型 YOLO 目标检测或目标缺失检测算法时，不应再修改客户端算法 ID 映射或发布新客户端版本。

### 2.2 本期范围

本期仅支持下列模型与运行方式：

- 单模型 Ultralytics YOLO `detect` 任务。
- 检测到目标时触发报警的通用目标检测。
- 指定目标持续未出现时触发报警的通用缺失检测。
- 服务端动态下发目标类别、置信度阈值、NMS 阈值、检测间隔、连续确认帧数、冷却时间、检测区域及通用跟踪开关。
- LabelKit 与业务后台部署在不同服务器时，通过业务后台 OpenAPI 和对象存储完成模型交付。

### 2.3 非本期范围

以下能力不得接入本期通用动态算法通道：

- 人数统计、累计计数和越线计数。
- 摔倒等姿态或关键点推理。
- 抽烟等多模型目标关联。
- 工作服、安全装备等人与物关系判断。
- OCR、车牌识别、人脸识别和特征库检索。
- 依赖连续时序的行为识别。
- 需要自定义 Python 后处理代码的算法。
- 训练平台自动决定并绑定生产摄像头。

上述复杂算法应继续采用显式客户端能力开发，或在后续另行建设经过签名、隔离和版本治理的插件机制。

## 3. 现状依据与关键问题

### 3.1 LabelKit 模型产物

LabelKit 当前在训练成功后复制本次训练的 `best.pt`，并创建独立的 `ModelVersion` 记录。现有模型版本已经包含项目、版本号、文件路径、指标、数据集快照、训练任务和数据集版本等基础信息，因此适合作为部署源对象。

本期应在现有模型版本之上补充部署视图和部署记录，不应另建一套与训练模型无关的模型目录。

### 3.2 业务后台现状

业务后台已经具备算法、模型、模型版本、策略、策略规则、摄像头策略绑定和客户端 `strategy3` 下发能力。新增部署功能应调用领域 Service 完成统一编排，不应由 LabelKit 依次调用现有管理端 CRUD 接口。

现有模型版本发布逻辑使用 `Long` 引用比较判断目标版本。该写法对大数值 ID 不可靠，存在目标版本未被正确发布的风险。此问题应在部署功能接入前修复，并补充回归测试。

### 3.3 Python 客户端现状

客户端已经能够轮询业务后台策略、下载模型、解析动态目标类别并加载 Ultralytics YOLO 模型，具备通用动态算法的基础条件。但现有模型切换流程在新模型加载前释放旧 Detector；如果下载或加载失败，旧模型也会停止工作。此外，策略处理器可能在首次加载失败后仍记录新模型集合，后续相同策略轮询无法稳定触发重试。

客户端部分报警路径还存在固定使用 `confidence > 0.5` 的行为，可能与服务端下发阈值不一致。上述问题决定了当前客户端只能覆盖理想路径，不能直接作为生产级无感热更新底座。

## 4. 第一性原理与方案选择

模型一键部署的本质不是“复制一个文件”，而是同时完成四项可观察结果：模型产物可靠交付、业务对象稳定映射、运行规则可回滚发布、客户端确认实际激活。缺少任意一项，都只能证明某个接口执行成功，不能证明新算法已经在业务摄像头上运行。

### 4.1 最小必要系统

满足目标所需的最小系统由以下部分组成：

1. 一个由业务后台提供的专用部署入口。
2. 一个可重试、可查询、可补偿的部署作业状态机。
3. 一组稳定的来源项目与业务对象映射。
4. 一个支持校验、预加载、原子切换和失败保底的客户端模型加载器。
5. 一条从客户端返回业务后台的模型激活回执链路。

### 4.2 方案比较

| 方案 | 可行性 | 主要问题 | 结论 |
|---|---|---|---|
| LabelKit 直接写业务数据库或共享目录 | 低 | 强耦合数据库结构，跨服务器困难，无法统一鉴权、补偿和审计 | 不采用 |
| LabelKit 串联现有算法、模型、版本、策略 CRUD | 中 | 多次调用可能部分成功，现有返回值不足以可靠获得全部资源 ID，幂等和回滚复杂 | 不采用 |
| 业务后台同步接收文件并一次完成全部操作 | 中 | 大文件、网络超时和对象存储操作无法与数据库形成真实事务 | 仅适合原型验证 |
| 业务后台部署作业 + 对象存储 + 客户端回执 | 高 | 需要新增状态和少量基础设施，但失败边界清晰、可恢复、可审计 | 本期采用 |
| 完整动态插件平台 | 中 | 能力强，但安全、签名、隔离和版本治理成本明显超过本期需求 | 后续按需评估 |

## 5. 总体架构

```text
LabelKit 模型中心
        │ 用户发起一次部署
        ▼
LabelKit 服务端部署编排
        │ OpenAPI：创建作业、上传文件、发布
        ▼
AI Box 业务后台部署中心
        ├── 部署状态机与幂等控制
        ├── 对象存储文件管理
        ├── 算法/模型/版本/策略/规则编排
        └── 发布、审计与回滚
        │
        │ strategy3 下发
        ▼
AI Box Python 客户端
        ├── 临时下载与摘要校验
        ├── 模型预加载和空帧预热
        ├── Detector 原子切换
        ├── 失败保留旧模型
        └── 激活状态回执
        │
        ▼
业务平台展示发布状态、设备生效状态和失败原因
```

“一键部署”表示用户只需要完成一次确认操作，不表示跨系统流程必须压缩为一个同步 HTTP 请求。LabelKit 服务端可以在一次用户操作后按部署协议连续完成创建作业、上传文件和请求发布。

## 6. 业务对象映射

### 6.1 映射规则

| LabelKit 对象 | 业务平台对象 | 映射要求 |
|---|---|---|
| 项目 | 算法、模型、默认策略 | 首次部署创建，后续部署稳定复用 |
| 模型版本 | 业务模型版本 | 每次训练部署新增一个版本 |
| 模型类别 | 规则 `targetClasses` | 以模型真实类别为准，部署前显式确认 |
| 检测方式 | 算法 `detectionType` | 目标出现或目标缺失 |
| 推理与报警参数 | 规则 `paramConfig` | 作为运行参数唯一来源 |
| 模型文件 | 对象存储文件 | 文件大小和 SHA-256 必须一致 |
| 摄像头 | 摄像头策略绑定 | 由业务平台人工配置 |

### 6.2 配置唯一来源

本期不得新增覆盖完整运行参数的 `runtimeProfile`。客户端运行行为应继续由业务平台现有字段统一表达：

- 算法的 `detectionType`。
- 规则的 `targetClasses`。
- 规则的 `enableTracking`。
- 规则的 `paramConfig`。
- 规则关联的 `modelVersionId`。

模型部署元数据只补充现有结构无法表达的内容：

- `modelFormat`：模型文件格式。
- `taskType`：模型任务类型，本期固定为 `detect`。
- `sha256`：模型文件摘要。
- `sourceModelVersionId`：LabelKit 模型版本标识。
- `minimumClientVersion`：最低兼容客户端版本。
- `classNames`：模型类别索引与名称映射。
- `artifactOrigin`：模型来源，本期自动发布只允许 `train`。

## 7. 数据结构设计

业务后台应复用现有算法、模型、模型版本、策略和策略规则表，并新增最小必要的集成记录。

### 7.1 来源绑定表 `alg_model_source_binding`

该表记录 LabelKit 项目与业务对象之间的稳定映射。

| 字段 | 说明 |
|---|---|
| `source_system` | 来源系统，固定使用 `LABELKIT` |
| `source_project_id` | LabelKit 项目 ID |
| `algorithm_id` | 业务算法 ID |
| `model_id` | 业务模型 ID |
| `strategy_id` | 默认策略 ID |
| `created_at`、`updated_at` | 创建和更新时间 |

应建立唯一约束：

```text
(source_system, source_project_id)
```

### 7.2 部署作业表 `alg_model_deployment`

该表记录一次来源模型版本的完整部署过程。

| 字段组 | 主要字段 |
|---|---|
| 来源信息 | `source_system`、`source_project_id`、`source_model_version_id` |
| 幂等信息 | `idempotency_key` |
| 模型信息 | `model_format`、`task_type`、`sha256`、`file_size`、`class_names` |
| 作业状态 | `status`、`failed_stage`、`retry_count` |
| 产出对象 | `file_id`、`algorithm_id`、`model_id`、`model_version_id`、`strategy_id`、`rule_id` |
| 失败信息 | `error_code`、`error_message` |
| 审计信息 | `open_api_client_id`、`created_at`、`updated_at`、`published_at` |

应建立唯一约束：

```text
(source_system, source_model_version_id)
```

### 7.3 激活记录表 `alg_model_activation`

该表记录已发布模型在具体设备和摄像头上的真实生效情况。

| 字段 | 说明 |
|---|---|
| `deployment_id` | 部署作业 ID |
| `device_id` | 客户端设备 ID |
| `camera_id` | 摄像头 ID |
| `rule_id` | 当前规则 ID |
| `model_version_id` | 待激活模型版本 ID |
| `status` | 下载、加载、激活或失败状态 |
| `client_version` | 客户端版本 |
| `actual_sha256` | 客户端实际文件摘要 |
| `error_code`、`error_message` | 失败原因 |
| `reported_at` | 最近上报时间 |

建议建立业务唯一约束：

```text
(device_id, camera_id, rule_id, model_version_id)
```

数据库变更应写入业务后台的 `document/sql/upgrade.sql`，不得修改管理员维护的完整 DDL 文件。新增表的基础 CRUD 应优先使用业务后台代码生成器生成，再补充部署领域逻辑。

## 8. 部署接口规格

### 8.1 鉴权要求

部署接口应使用独立的 OpenAPI 客户端身份，并增加 `MODEL_DEPLOY` 权限范围。LabelKit 浏览器端不得持有业务平台 AppSecret，所有部署调用必须由 LabelKit 服务端发起。

### 8.2 创建部署作业

```http
POST /openapi/model-deployments
Idempotency-Key: labelkit:{sourceModelVersionId}
Content-Type: application/json
```

请求示例：

```json
{
  "sourceSystem": "LABELKIT",
  "sourceProjectId": "project-id",
  "sourceModelVersionId": "model-version-id",
  "algorithmName": "灭火器检测",
  "modelName": "灭火器检测模型",
  "versionName": "v2",
  "taskType": "detect",
  "modelFormat": "pt",
  "artifactOrigin": "train",
  "sha256": "模型文件SHA-256",
  "fileSize": 12345678,
  "classNames": {
    "0": "灭火器"
  },
  "detectionType": 1,
  "targetClasses": ["灭火器"],
  "defaultParams": {
    "confidenceThreshold": 0.5,
    "nmsThreshold": 0.45,
    "detectionInterval": 5,
    "confirmFrames": 3,
    "cooldownSeconds": 30
  },
  "publishMode": "AUTO_IF_UNBOUND"
}
```

业务后台应返回 `deploymentId`、当前状态、是否首次部署及文件上传信息。相同来源模型版本或相同幂等键重复请求时，应返回原部署作业，不得创建重复资源。

### 8.3 上传模型文件

```http
PUT /openapi/model-deployments/{deploymentId}/artifact
Content-Type: application/octet-stream
```

业务后台应将文件流写入对象存储，完成后校验文件大小和 SHA-256。上传中断不应进入发布阶段，重新上传时应继续使用原 `deploymentId`。

如对象存储已经具备分片或预签名上传能力，可在不改变部署作业语义的前提下替换文件传输实现。

### 8.4 发布部署作业

```http
POST /openapi/model-deployments/{deploymentId}/publish
```

发布接口应完成资源校验、业务对象创建或复用、规则生成和发布。接口返回成功只表示业务平台发布完成，不代表客户端已经激活。

### 8.5 查询部署状态

```http
GET /openapi/model-deployments/{deploymentId}
```

响应应至少包含：

- 当前部署状态和失败步骤。
- 算法、模型、模型版本、策略和规则 ID。
- 是否首次部署。
- 当前受影响摄像头数量。
- 已激活、失败和等待激活的摄像头数量。
- 错误代码和可读错误信息。
- 是否允许重试或回滚。

### 8.6 重试与回滚接口

```http
POST /openapi/model-deployments/{deploymentId}/retry
POST /openapi/model-deployments/{deploymentId}/rollback
```

重试应从失败步骤继续执行，不得重新建立已成功且可复用的资源。回滚应将发布规则切回上一可用模型版本，不应删除失败版本和审计记录。

### 8.7 客户端激活回执

客户端应通过设备鉴权接口上报激活状态：

```http
POST /client/model-activations
```

回执应包含设备、摄像头、规则、模型版本、客户端版本、实际摘要、状态和错误信息。相同激活对象的重复上报应更新最近状态，不得产生无限重复记录。

## 9. 部署状态机与事务边界

### 9.1 部署状态

```text
RECEIVED
    │
    ▼
ARTIFACT_READY
    │
    ▼
RESOURCE_READY
    │
    ▼
PUBLISHED

任一步骤失败：FAILED
发布后撤销：ROLLING_BACK → ROLLED_BACK
```

状态定义如下：

| 状态 | 定义 |
|---|---|
| `RECEIVED` | 部署元数据已受理，尚未获得有效模型文件 |
| `ARTIFACT_READY` | 对象存储文件存在，大小和摘要校验一致 |
| `RESOURCE_READY` | 业务资源已经建立完整，但尚未对客户端发布 |
| `PUBLISHED` | 模型版本和策略规则已经发布 |
| `FAILED` | 某一步骤失败，保留失败阶段和可重试上下文 |
| `ROLLING_BACK` | 正在恢复上一条可用规则 |
| `ROLLED_BACK` | 业务规则已恢复，失败版本保留供排查 |

### 9.2 事务边界

对象存储写入和数据库写入不能构成同一个本地事务，因此不得将整个部署流程宣称为“一个事务”。

业务后台应按以下边界处理：

1. 对象存储上传成功后提交 `ARTIFACT_READY` 状态。
2. 算法、模型、模型版本、策略、规则及映射关系应尽可能在同一个数据库事务中创建或更新。
3. 数据库事务失败时，部署作业进入 `FAILED`，对象存储文件暂时保留并允许重试复用。
4. 发布失败时不得删除上一已发布规则。
5. 已发布后回滚时只切换发布关系，不立即物理删除新版本及其文件。
6. 孤立文件应由独立清理任务根据保留期处理，清理动作必须避开仍被部署记录或模型版本引用的文件。

## 10. 部署业务流程

### 10.1 LabelKit 部署前检查

LabelKit 服务端发起部署前应执行以下检查：

1. 模型版本存在且文件可读取。
2. 模型来源为训练任务产物，`artifactOrigin=train`。
3. 模型任务类型为 `detect`。
4. 模型类别映射非空，且用户选择的目标类别真实存在于模型类别中。
5. 文件扩展名、大小和 SHA-256 已计算完成。
6. 部署目标地址和服务端凭据已经配置。
7. 当前模型未处于正在部署状态。

任一检查失败时，应在 LabelKit 内直接阻止部署，不调用业务平台发布接口。

### 10.2 首次部署

首次部署应完成：

1. 创建算法。
2. 创建模型。
3. 创建首个模型版本并关联对象存储文件。
4. 创建默认策略。
5. 创建默认策略规则并绑定模型版本。
6. 发布算法、模型版本、策略及规则所需的有效状态。
7. 创建 LabelKit 项目来源映射。

首次部署不得创建摄像头策略绑定关系。

### 10.3 同项目版本更新

同一个 LabelKit 项目再次部署时应：

1. 复用来源映射中的算法、模型和默认策略。
2. 创建新的业务模型版本。
3. 创建关联新模型版本的候选规则。
4. 保留上一模型版本和上一规则作为回滚基线。
5. 根据发布模式决定是否立即切换发布规则。

当默认策略尚未绑定摄像头时，`AUTO_IF_UNBOUND` 可以自动发布。当策略已经影响摄像头时，LabelKit 应展示受影响摄像头数量，并要求用户明确确认“部署并更新现有策略”；未经确认时只创建候选版本，不应静默替换生产模型。

### 10.4 摄像头绑定

部署完成后，用户应进入业务平台检查新算法和默认策略，并在摄像头配置页面选择需要绑定的摄像头。业务平台现有的直接绑定和冲突校验逻辑应继续作为唯一绑定入口。

## 11. 客户端基础升级要求

客户端应进行一次生产级模型热更新改造。此改造是未来通用算法不更新客户端代码的必要前置条件。

### 11.1 通用算法处理

对于客户端未内置算法 ID，但服务端声明为本期通用能力的策略，客户端应进入通用 YOLO 处理器，不应因算法 ID 未出现在静态映射中而拒绝执行。

通用处理器只能读取以下受控配置：

- `detectionType`
- `targetClasses`
- `enableTracking`
- `paramConfig`
- `modelVersionId`
- `modelFileUrl`
- `modelFormat`
- `sha256`
- `minimumClientVersion`

如果策略要求客户端不具备的姿态、多模型、计数、越线或自定义后处理能力，客户端必须明确返回 `UNSUPPORTED_CAPABILITY`，不得降级为含义不同的普通目标检测。

### 11.2 安全热切换

客户端模型更新应按以下顺序执行：

1. 将新文件下载到临时路径。
2. 校验文件大小和 SHA-256。
3. 检查模型格式、任务类型和最低客户端版本。
4. 在不释放旧 Detector 的情况下创建候选 Detector。
5. 执行模型加载和空帧预热推理。
6. 全部成功后原子替换运行实例所使用的 Detector。
7. 新 Detector 正常运行后才减少旧 Detector 引用并释放资源。
8. 任一步骤失败时继续使用旧 Detector，并上报失败原因。

### 11.3 重试与缓存

客户端不得在模型首次加载失败后将其永久视为已处理。失败任务应使用带上限的指数退避重试，并在策略变化、网络恢复、进程重启或人工重试时重新执行。

每个运行实例至少应保留当前版本和上一可用版本。缓存清理不得删除正在使用、等待切换或作为回滚基线的模型文件。

### 11.4 参数一致性

通用报警路径应使用策略实际下发的置信度阈值，不得另行固定使用 `0.5`。如特定专用算法确实要求独立阈值，应使用明确的算法专属字段和能力声明，不得与通用阈值混用。

## 12. 发布状态与激活状态

业务后台应将“资源已发布”和“客户端已生效”作为两个独立事实展示。

### 12.1 客户端激活状态机

```text
PENDING → DOWNLOADING → LOADED → ACTIVE
                └──────────────→ FAILED
```

| 状态 | 含义 |
|---|---|
| `PENDING` | 规则已发布，等待客户端拉取 |
| `DOWNLOADING` | 客户端正在下载模型 |
| `LOADED` | 文件校验、模型加载和预热已完成 |
| `ACTIVE` | 运行实例已经原子切换到新模型 |
| `FAILED` | 下载、校验、兼容性、加载或切换失败 |

### 12.2 平台展示口径

平台应使用以下口径，避免把数据库发布成功误报为业务生效：

- 已发布，暂无摄像头绑定。
- 已发布，等待设备拉取。
- 部分摄像头已生效，例如“3/5 已生效”。
- 全部摄像头已生效。
- 部分失败，并展示设备、摄像头和错误原因。
- 已回滚至上一模型版本。

激活期限应根据真实设备基线确定，初始规则建议为：

```text
max(120 秒, 实测 P95 模型下载与加载耗时的 3 倍)
```

超过期限仍未收到回执时，应标记为超时，不得显示“全部生效”。

## 13. LabelKit 页面要求

### 13.1 模型中心入口

训练生成的模型版本应提供“一键部署”操作。非训练来源模型、任务类型不兼容模型或文件不存在的模型应禁用该操作，并展示明确原因。

### 13.2 部署配置

部署确认界面应展示并允许配置：

- 目标业务环境。
- 算法名称和说明。
- 模型版本及训练指标摘要。
- 模型真实类别和目标类别。
- 检测类型：目标出现或目标缺失。
- 置信度、NMS、检测间隔、连续确认帧数和冷却时间。
- 是否启用通用跟踪。
- 文件大小和 SHA-256 摘要。
- 是否首次部署。
- 更新版本时受影响的摄像头数量。

### 13.3 部署进度

页面应根据部署作业状态显示：

- 正在创建部署作业。
- 正在上传模型。
- 正在创建业务资源。
- 已发布，等待客户端激活。
- 已全部生效。
- 部署失败及失败阶段。
- 可重试或可回滚操作。

前端刷新或浏览器关闭后，应能根据 `deploymentId` 恢复进度，不得依赖单次页面会话维持部署状态。

## 14. 安全与审计要求

模型文件会在客户端推理进程中加载，属于高风险运行资产。部署通道应满足以下要求：

1. LabelKit 应使用独立 AppKey，且只授予模型部署所需权限。
2. AppSecret 只允许存放在 LabelKit 服务端配置或受控环境变量中。
3. 浏览器请求、接口响应、业务日志和异常堆栈不得包含 AppSecret。
4. 部署通信应强制使用 HTTPS。
5. 部署接口应限制文件格式、文件大小、请求频率和并发数量。
6. 每次部署、重试、发布和回滚均应记录来源客户端、操作者、模型摘要、资源 ID、时间和结果。
7. 可根据实际网络拓扑配置来源 IP 白名单。
8. 本期自动发布只接受 LabelKit 训练任务形成的模型版本，不接受用户手工上传的任意 `.pt` 文件。
9. 客户端应以业务后台下发摘要校验实际文件，摘要不一致时不得加载。
10. 模型校验和预加载过程不得运行在业务后台 Java 主进程中。

PyTorch `.pt` 文件存在反序列化信任风险。本期可以将受信任训练链路产生的 `.pt` 作为兼容性优先方案，同时必须在真实 AI Box 上评估 ONNX。只有 ONNX 在精度、GPU 支持、冷启动、推理延迟和稳定性方面通过门禁后，才可调整默认交付格式。

## 15. 失败处理与回滚

### 15.1 失败处理原则

- 上传失败：部署作业停留在 `RECEIVED` 或进入 `FAILED`，不得创建发布资源。
- 摘要失败：删除或隔离本次无效上传文件，不进入资源创建阶段。
- 资源创建失败：回滚本地数据库事务，保留可复用对象存储文件和失败记录。
- 规则发布失败：保留上一已发布规则，不影响现有客户端。
- 客户端下载失败：继续使用旧模型并重试。
- 客户端加载失败：继续使用旧 Detector，报告详细错误。
- 部分设备失败：平台显示部分生效，不得将整个部署标记为全部生效。

### 15.2 回滚原则

回滚应通过重新发布上一模型版本对应的规则完成。客户端轮询到回滚规则后，应优先使用本地保留的上一版本缓存完成恢复。

回滚不应立即删除新模型版本、模型文件、部署记录或激活记录，以保证问题可追溯。确认稳定并超过保留期后，再由受控清理任务处理无引用资产。

## 16. 实施阶段与门禁

### 16.1 阶段零：真实环境验证与契约冻结

本阶段应使用 LabelKit 真实训练模型和目标 AI Box 完成以下验证：

- 当前 `.pt` 模型能否在目标客户端环境稳定加载。
- LabelKit 与客户端 Ultralytics、PyTorch 和 CUDA 组合是否兼容。
- 模型类别名称能否被业务规则和客户端准确识别。
- PT 与 ONNX 的精度差异、冷启动时间、单帧延迟、显存和连续运行稳定性。
- 目标网络下模型上传、下载和加载的 P50、P95 耗时。
- 部署接口字段、错误码、发布模式和回滚语义。

通过标准：至少一种模型格式在目标 AI Box 上达到现有业务可接受精度和性能，并且接口契约不再存在会改变数据结构或发布流程的未决项。

验证失败时，应停止高成本跨系统开发，缩减模型格式或客户端运行范围后重新评估。

### 16.2 阶段一：现有阻塞缺陷修复

- 修复业务后台模型版本发布中的 `Long` 比较问题。
- 为发布逻辑补充目标版本、其他版本和大数值 ID 回归测试。
- 完成客户端候选加载、原子切换、失败保底、重试和缓存改造。
- 统一通用报警置信度阈值。
- 增加客户端能力版本和激活回执。

通过标准：故意提供损坏模型或不可访问地址时，旧模型持续推理，客户端产生可查询失败回执，恢复网络或修复文件后可以自动重试成功。

### 16.3 阶段二：业务后台部署中心

- 增加数据库增量脚本和基础 CRUD。
- 增加部署领域 Service、OpenAPI、状态查询、重试和回滚。
- 接入对象存储并实现摘要校验。
- 实现来源映射、幂等和本地事务。
- 增加 OpenAPI 权限范围、审计和限流。
- 增加发布状态与激活状态展示接口。

通过标准：接口测试覆盖首次部署、重复请求、版本更新、上传中断、数据库失败、发布失败和回滚；所有写接口均通过后续查询完成数据断言。

### 16.4 阶段三：LabelKit 一键部署

- 增加 LabelKit 服务端部署配置和 API 客户端。
- 增加部署前检查、摘要计算和三步部署编排。
- 增加模型中心部署入口、确认界面和进度界面。
- 增加部署记录查询、恢复、重试和回滚入口。
- 增加同项目映射和受影响摄像头提示。

通过标准：用户只需在 LabelKit 完成一次部署确认，即可在业务平台看到正确的算法、模型、版本、策略和规则，不需要手工复制文件或重复录入。

### 16.5 阶段四：联调与灰度

- 使用测试算法完成首次部署。
- 在业务平台核对全部业务对象及关联关系。
- 绑定一台测试摄像头并确认客户端激活回执。
- 注入断网、损坏文件、错误摘要、版本不兼容、客户端重启和业务后台重启。
- 验证版本更新和回滚。
- 灰度到少量生产摄像头并观察稳定性。

通过标准：成功路径、失败路径和回滚路径全部通过，连续观察期内无旧模型中断、重复资源、错误全量生效状态或无法恢复的部署作业。

## 17. 测试与验收要求

### 17.1 核心验收用例

| 编号 | 场景 | 操作 | 预期结果 |
|---|---|---|---|
| A-01 | 首次部署 | 部署一个从未进入业务平台的 LabelKit 项目模型 | 只创建一套算法、模型和默认策略，不绑定摄像头 |
| A-02 | 幂等重试 | 对同一模型版本连续提交或超时后重试 | 返回同一部署作业，不产生重复业务资源 |
| A-03 | 版本更新 | 同项目训练并部署新版本 | 复用算法、模型和策略，只新增模型版本和规则 |
| A-04 | 文件损坏 | 上传与声明摘要不一致的文件 | 阻止发布，记录摘要校验失败 |
| A-05 | 上传中断 | 上传过程中断开网络后重试 | 继续原部署作业，不重复创建资源 |
| A-06 | 数据库失败 | 对象存储成功后模拟资源事务失败 | 作业可重试，对象存储文件可复用，无半套业务资源 |
| A-07 | 客户端下载失败 | 发布不可访问的模型地址 | 旧模型继续运行，客户端上报失败并重试 |
| A-08 | 客户端加载失败 | 下发无法加载的模型文件 | 旧 Detector 不释放，平台显示加载失败 |
| A-09 | 客户端重启 | 在下载或加载过程中重启客户端 | 重启后根据策略和本地状态继续激活 |
| A-10 | 激活确认 | 绑定测试摄像头并等待策略轮询 | 平台从等待激活变为该摄像头已生效 |
| A-11 | 回滚 | 新版本部分设备激活失败后执行回滚 | 客户端恢复上一模型，失败版本仍可追溯 |
| A-12 | 动态算法 | 新增一个普通 YOLO 检测算法，不修改客户端映射 | 通用处理器完成检测和报警 |
| A-13 | 越界能力 | 将姿态或多模型算法标记为通用算法 | 客户端拒绝执行并返回能力不支持 |
| A-14 | 凭据保护 | 检查浏览器请求、响应和服务日志 | 不出现业务平台 AppSecret |

### 17.2 定量验收要求

1. 同一来源模型版本重复部署时，业务模型版本、规则和部署作业重复新增数量应为 0。
2. 新模型下载或加载失败时，旧模型推理中断次数应为 0。
3. 文件摘要不一致时，进入 `PUBLISHED` 状态的次数应为 0。
4. 已绑定且在线的测试客户端应在激活期限内形成 `ACTIVE` 或明确的 `FAILED` 回执，未知状态不得被计入生效数量。
5. 回滚指令发布后，在线客户端应在两次策略轮询内开始恢复上一模型；最终恢复时间应结合真实模型加载基线验收。
6. 新增通用目标检测算法时，客户端算法 ID 静态映射修改数量应为 0。

## 18. 运维与可观测性

业务后台应记录以下关键日志和指标：

- 每个部署阶段的开始、成功、失败和耗时。
- 模型文件大小、摘要校验结果和对象存储文件 ID。
- 来源模型版本与业务对象 ID 映射。
- 幂等命中次数和失败重试次数。
- 发布后待激活、已激活、失败和超时设备数量。
- 客户端模型下载、加载、预热和切换耗时。
- 回滚发起人、原因、目标版本和完成结果。

应对部署失败率、激活超时率、摘要失败、客户端版本不兼容和连续重试失败建立告警。日志不得记录模型文件内容、AppSecret 或摄像头密码。

以下为一名熟悉三个项目的开发人员顺序实施的初步估算，不包含无法控制的现场设备和网络等待时间。

| 阶段 | 预计工作量 |

## 20. 风险与实施决策

| 风险或决策 | 当前处理方式 | 验证失败后的处置 |
|---|---|---|
| PT 与客户端运行环境兼容性 | 在阶段零使用真实模型和目标设备验证 | 固定兼容版本，或评估 ONNX |
| `.pt` 反序列化安全风险 | 只允许受信任训练产物，校验来源和摘要 | 停止自动发布 PT，切换安全格式评估 |
| 新模型导致旧模型中断 | 候选加载成功后原子切换 | 保持旧模型并上报失败 |
| 跨系统部分成功 | 部署作业、幂等、本地事务和补偿 | 从失败阶段重试或回滚 |
| 发布成功但客户端未生效 | 发布和激活状态分离 | 超时告警、重试或回滚 |
| 通用算法能力被过度解释 | 固定能力白名单，客户端显式拒绝越界能力 | 转为专用客户端开发 |
| 新版本影响已有生产摄像头 | 展示影响数量并要求明确确认 | 仅保存为候选版本 |

## 21. 实施结论

本方案采用“LabelKit 服务端发起、业务后台统一编排、对象存储承载模型、客户端安全激活、业务平台观测结果”的责任划分。该方案保留现有业务平台的算法、模型、策略和摄像头绑定体系，避免数据库直连、共享目录和多 CRUD 串联造成的强耦合，同时通过部署状态机、幂等、回滚和激活回执补齐跨系统部分成功问题。

本方案可以进入阶段零验证和阶段一基础缺陷修复。在真实目标 AI Box 的模型格式、性能和兼容性门禁通过前，不得直接进入生产发布。完成一次客户端基础升级后，后续通用单模型 YOLO 目标检测和目标缺失检测算法可以通过模型与策略配置动态接入；复杂后处理算法仍需显式开发，不属于本期无代码更新承诺。
